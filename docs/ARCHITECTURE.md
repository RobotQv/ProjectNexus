# 后端架构与事务说明

## 最新需求与当前实现的区别

下文包含既有后端基线与新增 v2 流程。最终业务以 [需求记录](REQUIREMENTS.md) 为准：AI 助手工具编排归工作流；主 RAG 清洗正文供检索和结构化提取复用；风险模块可供工作流分析候选依赖。

两个对话入口的任务建议先由提交者核对，再逐条正式审核；文档提取结果直接逐条正式待审。任意有效项目成员可正式审核，包括提交者本人。后端负责提交者/来源/审核追溯，支持已有任务各业务字段更新，生效时保存完整任务快照。当前操作审计不等于完整任务历史。

对话入口、预审状态、任务更新建议、完整历史、候选风险输入和正式数据变化后自动检查已接入。风险仅标记和提示，不定时检查、不自动改任务状态、不发送外部通知。现有普通业务校验与风险提示是不同机制，启动依赖关卡的既有业务校验仍保留。

## 本地开发和模块归属

每位组员运行自己的一套服务/数据库，不跨网络连接组长电脑。app 为后端工作区，frontend 为前端，tests 为集成测试，三位算法负责人分别在 team_modules/main_rag、workflow、risk 开发。每个工作区的 README 说明需求和验收。

公共协议/数据类型/错误已独立到 shared，不能反向依赖 app 或算法实现。算法工作区只导入 shared 和自身实现，team_modules/factory.py 是唯一跨算法装配点；旧 app.integrations.contracts 路径兼容导出同一个类型，不改变 API 或数据库字段。模块作者可用 DTO + 假 Provider 单测，无须 HTTP、业务数据库或登录账号。

共享代码通过合并同步，各人的 .env、账号、SQLite、上传文件和派生索引仍独立；不提交或合并运行数据。实际业务权限保留项目成员范围，所有有效项目成员均可协作编辑，与开发角色无关。

## 调用方向

```text
Vue / 手机浏览器
  → FastAPI /api/v1（JWT + 项目范围）
    → Service（唯一正式业务写入入口）
      → SQLite（业务数据 + Job + 审计）
      → 模块协议 → 主 RAG / 实体与工作流 / 风险模块
      → LLMProvider → 配置的 GLM 服务

独立 Worker
  → SQLite 领取一个 Job
  → 释放数据库事务后调用组员模块
  → 校验租约、来源与契约
  → 短事务发布结果
```

HTTP 路由是同步 `def`，FastAPI 在线程池执行阻塞 I/O；不会把同步模型调用塞进异步事件循环。每个 HTTP 请求和每个 Worker 阶段有自己的 Session，不跨线程共享。模型客户端由应用工厂创建，应用结束时关闭。

## 业务写事务

`write_scope()` → `begin_write()` → `BEGIN IMMEDIATE` → 重新校验有效用户/成员/项目 → 读取对象与 version → 验证 → 修改对象 + 审计 + Job → commit。

SQLite 同时只允许一个写事务；在读取依赖图和 expected_version 之前拿写锁，防止“两边分别校验无环但合在一起形成环”或“两个请求看到同一个旧版本都成功”。失败会随 Session 关闭 rollback，不会留下半个任务或半条审核结果。

这是适合当前 SQLite 的实现，不是可原样搬到高并发 MySQL 的通用方案。换数据库时必须重新实现 CAS / 行锁、依赖图并发保护和 Job 领取策略，并重跑并发测试。

## 资料、索引与工作流

1. 接口检查身份与文件类型，将文件保存到后端随机路径；原文件名只做展示。
2. 短写事务创建 Document + document_ingest Job，响应 202。
3. Worker 解析，主干校验段号并保存 DocumentBlock；解析状态 ready。
4. 主 RAG 使用这些带 ID 的 Block 建索引，返回索引回执；主干记录版本与数量后把索引标 ready。
5. 提取/摘要任务锁定文档版本，读取同一份 Block 和实体目录。结果先保存 Suggestion 或 summary，不直接改任务。
6. 确认建议时，重新校验来源、目标字段与版本，在同一事务创建/更新对象、保存完整 TaskHistory、排风险检查 Job，并写回 target_id。

对话不依赖文档：POST /assistant/messages 先保存请求及提交者，再在无数据库事务时调用 workflow.respond(request, BoundTools)。结果独立保存为 draft，由提交者核对提交后变 pending；文档结果直接 pending。所有有效项目成员均可正式审核。request_key 保证同一用户同一请求不重复生成；请求键与内容冲突返回 409。对话失败保留失败记录；新生成使用新 request_key。

解析成功、索引失败时重试不重复解析，Block ID 保持稳定。工作流 Run 每个 `document_id + version + kind` 唯一；已发布结果的 Job 重试不重复产生建议。需要重新设计提示词并重新运行同一版本时，应扩展明确的 run_revision / prompt_version 机制，不能悄悄覆盖已经审核的建议。

删除资料先软删除，所有读取/检索结果立即按业务状态过滤，再排队调用主 RAG 的 delete。清理失败在 Job 中可见；原始文件和 Block 仍保留在本机审计区。主 RAG 的向量索引不是资料是否可读的最终依据。

## Job 故障语义

- 状态：queued → running → succeeded / failed。
- 串行消费：即使误启动两个 Worker，也会在数据库写锁内检查是否已有未过期 running Job。
- 租约 120 秒、心跳间隔 30 秒。中断后超时任务标 failed，前端可手动重试；不是无限自动重跑。
- 发布前校验随机 lease_token，旧 Worker 不能覆盖另一次执行的数据库结果。
- 外部调用是**至少一次**，不承诺“恰好一次”。向量 upsert/delete、实体同步必须幂等；发生网络分区时外部旧调用仍可能晚返回，所以还须在检索时校验 Document 有效性。
- 模块调用过程中不持有业务写锁。模型/索引处理不能直接 import Session 并长时间锁住业务库。

Job 与业务修改同事务创建，相当于轻量事务发件箱。只改进度/状态不重新生成任务文本索引；标题、说明、模块、标签、别名变更才排新任务。Worker 实际读取最新实体文本，已删任务/移除成员以 `is_active=false` 同步。

## 查询与来源安全

新助手由工作流 respond 编排，BoundTools 每次调用独立会话并重新鉴权，提供任务检索、实体目录/定位、资料检索、项目快照和候选风险预览；不提供正式写入/批准工具。下面的固定查询路径仅用于兼容 /queries：先鉴权 → 判路由/集合 → 轻 RAG 候选 → SQLite 回源 → 主 RAG 证据 → 可选 Snapshot 分析 → 可选模型组织语言 → 再次鉴权和校验。

- 明确给出任务 ID 时只读该项目内任务，不能越权指定其他项目 ID。
- 有多个候选时返回 clarify；score 不是正确率，不写死虚构阈值。
- “所有未完成任务”使用 SQL 集合条件，而不是 Top-1 实体匹配。分页限制也约束回答数据量。
- 主干验证引用对应的文档、版本、Block ID 及摘录确实来自正文。模型只返回文字，程序认可的 evidence 由主干构造。
- 无资料返回 insufficient；部分能力不可用返回 partial / warnings，不用模型补造原因。
- 外部处理期间若任务更新，facts 再次回源；不把此前生成的旧状态叙述当最新结果。
- 历史 QueryRun / AnalysisRun 是可追踪记录，不等于现在的项目状态。获取历史记录仍要求当前项目成员权限。

## 数据归属

业务 SQLite 是 User、Project、ProjectMember、Task、Dependency、Document、Block、Suggestion、Risk 的权威来源。向量库只保存可重建的派生索引。规则结果绑定输入快照、日期和 rule_version；人工风险事项有自己的解决状态，互不覆盖。

所有操作时间存 UTC；SQLite 读回时补 UTC 标记。计划/预计/截止用 Date，时区由 Project 决定。规则日期当天是否超期必须按审计约定处理，不能用服务器当前小时猜测。

## 运行边界

当前不提供多机共享 SQLite、权限细分到单条任务、刷新令牌、全文版本覆盖、实时 SSE、病毒扫描和生产限流。AuditEvent 保存操作编号/类型/版本，新增 TaskHistory 保存每次任务生效后的完整快照；API 不返回内部存储路径、租约令牌、密码哈希或供应商原始异常文本。
